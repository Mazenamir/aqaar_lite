النظام عبارة عن منصة سحابية متعددة الشركات (**Multi-Tenant**) لإدارة مبيعات الوحدات العقارية، الحجوزات المؤقتة المتزامنة، صياغة واعتماد العقود وجداول الأقساط، وتحصيل الدفعات المالية بدقة متناهية دون استخدام الأعداد العشرية (**Zero Floating-Point**)، مع واجهات مطابقة بنسبة 100% لتصاميم **Stitch** المعتمدة باللغة العربية ودعم كامل لاتجاه اليمين لليسار (RTL).

## التشغيل بخطوة واحدة (Docker Compose)

تم تجهيز بيئة التشغيل بالكامل لتعمل بأمر واحد على أي جهاز نظيف يمتلك Docker و Docker Compose:

```bash
# 1. استنساخ المشروع
git clone <repository-url>
cd GreenRyad

# 2. تشغيل قاعدة البيانات والتطبيق
docker compose up --build
```

يقوم `docker compose up` تلقائياً بـ:
1. تشغيل حاوية `PostgreSQL 16` وإجراء الفحص الصحي `healthcheck`.
2. تشغيل الحاوية المجمعة `aqar_lite_app` عبر `Dockerfile` متعدد المراحل (Multi-stage build).
3. تطبيق الترحيلات المالية (`prisma migrate deploy`).
4. زرع البيانات الأولية الكاملة للشركتين والمستخدمين والوحدات والعقود (`prisma db seed`).
5. إتاحة النظام على الرابط: **`http://localhost:3000`**

## التشغيل المحلي للتطوير (npm run dev)

إذا أردت تشغيل بيئة التطوير محلياً:

### المتطلبات المسبقة:
- Node.js 20+
- PostgreSQL (على المنفذ الافتراضي 5432 أو 5434 حسب ضبطك)

# تثبيت الاعتماديات

npm run dev

## القرارات المعمارية والتقنية (Architecture & Technical Rationale)

### 1. العزل التام بين الشركات (Multi-Tenancy Isolation)
- **القرار**: استخدام نموذج العزل على مستوى السجلات (Row-Level Multi-Tenancy) مع قيد أمني صارم: **لا يُقبل أبداً `companyId` من مدخلات العميل أو معلمات الـ API**.
- **التنفيذ**: يتم استخراج `companyId` حصرياً من جلسة المستخدم الموثقة والمشفرة في الخادم (`session.user.companyId`). كافة الاستعلامات (`findMany`, `count`) والمعاملات (`create`, `update`, `transaction`) تتضمن شرط `where: { companyId }` دون استثناء.

### 2. الحسابات المالية الدقيقة (Zero Floating-Point Architecture)
- **القرار**: منع استخدام الأعداد العشرية (float / double) منعاً باتاً في قاعدة البيانات، وشفرة المصدر، ونماذج JSON.
- **التنفيذ**:
  - تخزين كافة المبالغ بالهللة السعودية كأعداد صحيحة (`BigInt` في Prisma و `BIGINT` في PostgreSQL). 1 ريال = 100 هللة.
  - العمليات الحسابية والتقسيم والخصم تتم عبر دوال دقيقة بالكامل في [`src/lib/money.ts`](file:///d:/WORK/Projects/GreenRyad/src/lib/money.ts).
  - عند الإرسال عبر JSON إلى الواجهة، تُرسل كـ `string` وكسور منسقة مثل `amountSar: "15,200.00"` لتفادي أخطاء التقريب في JavaScript (`0.1 + 0.2 !== 0.3`).

### 3. حساب الأقساط ومعالجة كسور الهللات
- **الشرط الصارم**: الدفعة الأولى + مجموع الأقساط = السعر النهائي تماماً بالهللة (0 تسامح).
- **التنفيذ**: يتم تقسيم المبلغ المتبقي على عدد الشهور، ويُحسب باقي القسمة الصحيحة للهللات (`remainderHalalas = remaining % count`). يضاف هذا الكسر بالكامل إلى **القسط الأول** فقط، بينما تتساوى بقية الأقساط بالهللة.

### 4. تقريب تواريخ الاستحقاق لنهاية الشهر (Month-End Clamping)
- **المعضلة**: إذا بدأ العقد يوم 31 يناير، فإن شهر فبراير لا يحتوي على يوم 31.
- **الحل**: تنفيذ خوارزمية ذكية في `InstallmentService`: لكل شهر لاحق، يتم جلب أقصى عدد أيام متاح في ذلك الشهر، ويتم ضبط تاريخ الاستحقاق على `Math.min(targetDay, daysInMonth)`. بالتالي: 31 يناير -> 28 فبراير (أو 29 في السنة الكبيسة) -> 31 مارس -> 30 أبريل.

### 5. حماية الحجوزات من التعارض التزامني (Concurrency & Race Conditions)
- **المعضلة**: محاولة مندوبي مبيعات حجز نفس الوحدة في نفس الجزء من الثانية.
- **الحل**: استخدام التحديث الشرطي الذري (Atomic Conditional Update) داخل معاملة قاعدة البيانات:
  ```typescript
  const updated = await tx.unit.updateMany({
    where: { id: unitId, companyId, status: "AVAILABLE" },
    data: { status: "RESERVED" }
  });
  if (updated.count === 0) throw new Error("الوحدة محجوزة أو مباعة بالفعل");
  ```
  عملية التحديث الذري تعتمد على أقفال الصفوف في محرك PostgreSQL، مما يمنع الحجز المزدوج بنسبة 100%.

### 6. توزيع المدفوعات التلقائي (FIFO Allocation) ومنع التكرار (Idempotency)
- **التنفيذ**:
  - عند تسجيل أي دفعة، يتم التحقق أولاً من مفتاح منع التكرار (`idempotencyKey`). إذا تكرر الطلب (بسبب انقطاع اتصال أو نقر مزدوج)، يعيد الخادم العملية الأصلية فوراً دون إنشاء دفعة مكررة أو تكرار خصم الأقساط.
  - توزيع المبلغ المحصل يتم بنظام **FIFO** عبر الأقساط غير المسددة ذات تاريخ الاستحقاق الأقدم أولاً.
  - فحص سقف المبالغ: لا يمكن أن يتجاوز مجموع المدفوعات الرصيد المتبقي الإجمالي للعقد.

## الافتراضات الموثقة (Documented Assumptions)

1. **انتهاء الحجز بعد 72 ساعة**:
   - يتم تحديد `expiresAt` تلقائياً بـ `now + 72 hours`.
   - يتم تنفيذ مسح دوري وتلقائي (Lazy Cleanup & Sweeper) عند كل عملية استعلام أو حجز للوحدات لتحويل الحجوزات المنتهية إلى `EXPIRED` وإعادة الوحدة تلقائياً إلى حالة `AVAILABLE`.
2. **سقف الخصم 5%**:
   - تم تقييد الخصم في 3 طبقات دفاعية:
     1. قيد قاعدة البيانات: `CONSTRAINT "discount_max_5_percent" CHECK ("discountPercent" <= 5)`.
     2. طبقة التحقق البرمجية (Zod Schema & Service): رفض أي قيمة > 5 برمز خطأ `400 Bad Request`.
     3. واجهة المستخدم (UI): التحقق اللحظي والتنبيه الصريح للمستخدم.
3. **اعتماد العقد يغير حالة الوحدة**:
   - يتم إجراء اعتماد العقد في معاملة موحدة (`tx`) تحول العقد إلى `APPROVED` والوحدة إلى `SOLD` وتسجل في سجل الرقابة `AuditLog`.

## أبرز 3 مخاطر أمنية وكيفية معالجتها (Security Risks & Mitigations)

### الخطر 1: تسريب بيانات بين الشركات (Broken Object Level Authorization / IDOR)
- **التهديد**: قيام مستخدم بتغيير معرف الوحدة أو العقد في الطلب للوصول إلى بيانات شركة أخرى.
- **المعالجة**: عزل كامل في طبقة الخدمة `Service Layer`؛ يتم تضمين `companyId` المستخرج من الـ Session في كل استعلام قاعدة بيانات. تم كتابة اختبار آلي مخصص [`tests/security-isolation.test.ts`](file:///d:/WORK/Projects/GreenRyad/tests/security-isolation.test.ts) للتحقق من استحالة وصول شركة A لبيانات شركة B.

### الخطر 2: هجمات التسابق وتكرار العمليات (Race Conditions & Double Spending)
- **التهديد**: إرسال نقرتين متزامنتين لتسجيل دفعة أو حجز وحدة.
- **المعالجة**:
  - للحجوزات: تحديث ذري مشروط (`updateMany where status = AVAILABLE`).
  - للمدفوعات: فرض قيد فريد `UNIQUE(idempotencyKey)` في قاعدة البيانات وداخل معاملة ذرية.

### الخطر 3: التلاعب بالأسعار أو تعديل سجلات التدقيق (Data Tampering & Privilege Escalation)
- **التهديد**: تعديل سعر وحدة محجوزة أو مباعة، أو قيام موظف بحذف أفعاله من سجل الرقابة.
- **المعالجة**:
  - منع تعديل سعر أي وحدة حالتها ليست `AVAILABLE` عبر شروط برمجية وقيد تدقيق إلزامي `AuditLog` يسجل السعر القديم والجديد وهوية المعدل.
  - جعل سجل الرقابة (`AuditLog`) حقلاً للإضافة فقط (Append-Only Ledger)، ولا يُتاح الوصول إليه إلا لدور `COMPANY_ADMIN`.
