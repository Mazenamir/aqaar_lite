# عقار لايت (Aqar Lite) - نظام مبيعات العقارات بالتقسيط

<div dir="rtl" align="right">

مشروع الاختبار التقني لوظيفة مطور متكامل (Full-Stack Developer) - **شركة الريادة الخضراء**
المعرف المرجعي: `RA-HR-2026-1110`

النظام عبارة عن منصة سحابية متعددة الشركات (**Multi-Tenant**) لإدارة مبيعات الوحدات العقارية، الحجوزات المؤقتة المتزامنة، صياغة واعتماد العقود وجداول الأقساط، وتحصيل الدفعات المالية بدقة متناهية دون استخدام الأعداد العشرية (**Zero Floating-Point**)، مع واجهات مطابقة بنسبة 100% لتصاميم **Stitch** المعتمدة باللغة العربية ودعم كامل لاتجاه اليمين لليسار (RTL).

## التشغيل بخطوة واحدة (Docker Compose)

تم تجهيز بيئة التشغيل بالكامل لتعمل بأمر واحد على أي جهاز نظيف يمتلك Docker و Docker Compose:

```bash
# 1. استنساخ المشروع
git clone <repository-url>
cd GreenRyad

# 2. تشغيل قاعدة البيانات والتطبيق
docker compose up --build
```

يقوم `docker compose up` تلقائياً بـ:
1. تشغيل حاوية `PostgreSQL 16` وإجراء الفحص الصحي `healthcheck`.
2. تشغيل الحاوية المجمعة `aqar_lite_app` عبر `Dockerfile` متعدد المراحل (Multi-stage build).
3. تطبيق الترحيلات المالية (`prisma migrate deploy`).
4. زرع البيانات الأولية الكاملة للشركتين والمستخدمين والوحدات والعقود (`prisma db seed`).
5. إتاحة النظام على الرابط: **`http://localhost:3000`**

## القرارات المعمارية والتقنية (Architecture & Technical Rationale)

### 1. العزل التام بين الشركات (Multi-Tenancy Isolation)
- **القرار**: استخدام نموذج العزل على مستوى السجلات (Row-Level Multi-Tenancy) مع قيد أمني صارم: **لا يُقبل أبداً `companyId` من مدخلات العميل أو معلمات الـ API**.
- **التنفيذ**: يتم استخراج `companyId` حصرياً من جلسة المستخدم الموثقة والمشفرة في الخادم (`session.user.companyId`). كافة الاستعلامات (`findMany`, `count`) والمعاملات (`create`, `update`, `transaction`) تتضمن شرط `where: { companyId }` دون استثناء.

### 2. الحسابات المالية الدقيقة (Zero Floating-Point Architecture)
- **القرار**: منع استخدام الأعداد العشرية (float / double) منعاً باتاً في قاعدة البيانات، وشفرة المصدر، ونماذج JSON.
- **التنفيذ**:
  - تخزين كافة المبالغ بالهللة السعودية كأعداد صحيحة (`BigInt` في Prisma و `BIGINT` في PostgreSQL). 1 ريال = 100 هللة.
  - العمليات الحسابية والتقسيم والخصم تتم عبر دوال دقيقة بالكامل في [`src/lib/money.ts`](file:///d:/WORK/Projects/GreenRyad/src/lib/money.ts).
  - عند الإرسال عبر JSON إلى الواجهة، تُرسل كـ `string` وكسور منسقة مثل `amountSar: "15,200.00"` لتفادي أخطاء التقريب في JavaScript (`0.1 + 0.2 !== 0.3`).

### 3. حساب الأقساط ومعالجة كسور الهللات
- **الشرط الصارم**: الدفعة الأولى + مجموع الأقساط = السعر النهائي تماماً بالهللة (0 تسامح).
- **التنفيذ**: يتم تقسيم المبلغ المتبقي على عدد الشهور، ويُحسب باقي القسمة الصحيحة للهللات (`remainderHalalas = remaining % count`). يضاف هذا الكسر بالكامل إلى **القسط الأول** فقط، بينما تتساوى بقية الأقساط بالهللة.

### 4. تقريب تواريخ الاستحقاق لنهاية الشهر (Month-End Clamping)
- **المعضلة**: إذا بدأ العقد يوم 31 يناير، فإن شهر فبراير لا يحتوي على يوم 31.
- **الحل**: تنفيذ خوارزمية ذكية في `InstallmentService`: لكل شهر لاحق، يتم جلب أقصى عدد أيام متاح في ذلك الشهر، ويتم ضبط تاريخ الاستحقاق على `Math.min(targetDay, daysInMonth)`. بالتالي: 31 يناير -> 28 فبراير (أو 29 في السنة الكبيسة) -> 31 مارس -> 30 أبريل.

### 5. حماية الحجوزات من التعارض التزامني (Concurrency & Race Conditions)
- **المعضلة**: محاولة مندوبي مبيعات حجز نفس الوحدة في نفس الجزء من الثانية.
- **الحل**: استخدام التحديث الشرطي الذري (Atomic Conditional Update) داخل معاملة قاعدة البيانات:
  ```typescript
  const updated = await tx.unit.updateMany({
    where: { id: unitId, companyId, status: "AVAILABLE" },
    data: { status: "RESERVED" }
  });
  if (updated.count === 0) throw new Error("الوحدة محجوزة أو مباعة بالفعل");
  ```
  عملية التحديث الذري تعتمد على أقفال الصفوف في محرك PostgreSQL، مما يمنع الحجز المزدوج بنسبة 100%.

### 6. توزيع المدفوعات التلقائي (FIFO Allocation) ومنع التكرار (Idempotency)
- **التنفيذ**:
  - عند تسجيل أي دفعة، يتم التحقق أولاً من مفتاح منع التكرار (`idempotencyKey`). إذا تكرر الطلب (بسبب انقطاع اتصال أو نقر مزدوج)، يعيد الخادم العملية الأصلية فوراً دون إنشاء دفعة مكررة أو تكرار خصم الأقساط.
  - توزيع المبلغ المحصل يتم بنظام **FIFO** عبر الأقساط غير المسددة ذات تاريخ الاستحقاق الأقدم أولاً.
  - فحص سقف المبالغ: لا يمكن أن يتجاوز مجموع المدفوعات الرصيد المتبقي الإجمالي للعقد.

### 7. نظام المصادقة وإدارة الجلسات والأمان (Phase 3: Authentication & Security)
- **تشفير كلمات المرور (Password Hashing)**:
  - استخدام خوارزمية **Argon2id** (الموصى بها أمنياً من OWASP و RFC 9106) بمعلمات مشددة: `memoryCost: 19MB`, `timeCost: 2`, `parallelism: 1`.
  - تنفيذ فحص توقيتي وهمي (`dummyVerifyPassword`) لحماية النظام من هجمات التخمين عبر قياس زمن الاستجابة (Timing Attacks).
- **إدارة الجلسات (PostgreSQL-Backed Sessions)**:
  - توليد معرفات جلسة عشوائية مشفرة تحتوي على 256 بت من الإنتروبيا (`crypto.randomBytes(32).toString('base64url')`).
  - تخزين **تجزئة SHA-256** فقط لمعرف الجلسة في قاعدة البيانات (`sessionTokenHash`)؛ لا يتم حفظ التوكن الصريح نهائياً لحماية الجلسات في حال حدوث تسريب لقاعدة البيانات.
  - دعم إلغاء الجلسات اللحظي (`revocation`) عند تسجيل الخروج مع تسجيل `revokedAt`.
  - رفض الجلسات المنتهية صلاحيتها تلقائياً (مدة الجلسة 7 أيام).
- **أمان ملفات تعريف الارتباط (Cookie Security Configuration)**:
  - `HttpOnly: true` لمنع سرقة الجلسة عبر هجمات XSS.
  - `Secure: true` في بيئات الإنتاج (عبر بروتوكول HTTPS).
  - `SameSite: Lax` لمنع هجمات تزوير الطلبات عبر المواقع (CSRF).
  - `Path: /` مع تحديد `maxAge` مطابق لانتهاء الجلسة.
- **الحماية من هجمات القوة الغاشمة (Rate Limiting & Brute-Force Protection)**:
  - محدد معدل ذكي يمنع المحاولات بعد 5 إخفاقات متتالية لمدة 15 دقيقة مع إرجاع `429 Too Many Requests` وترويسة `Retry-After`.
  - إعادة تعيين العداد فور نجاح تسجيل الدخول.
  - رسائل أخطاء عامة وغير كاشفة (`"بيانات الاعتماد غير صحيحة"`) تتطابق تماماً في حال عدم وجود البريد الإلكتروني أو خطأ كلمة المرور لمنع استكشاف الحسابات (Account Enumeration).
- **حماية تزوير الطلبات عبر المواقع (CSRF & Origin Protection)**:
  - فحص ترويسات `Origin` و `Referer` على كافة الطلبات المعدلة للحالة (`POST`, `PUT`, `PATCH`, `DELETE`) ومطابقتها لمضيف التطبيق المعتمد.
- **مصفوفة الصلاحيات (Role-Based Access Control - RBAC)**:
  - **`COMPANY_ADMIN`**: إدارة الوحدات وتعديل الأسعار، الاطلاع على بيانات الشركة، وقراءة سجلات التدقيق.
  - **`SALES_AGENT`**: إدارة العملاء المملوكين له، حجز الوحدات، إنشاء مسودات العقود (ولا يملك اعتمادها أو تسجيل الدفعات أو تعديل الأسعار).
  - **`ACCOUNTANT`**: اعتماد العقود وتحويل حالة الوحدات إلى مباعة، تسجيل سندات القبض وتوزيع الدفعات (ولا يملك تعديل الأسعار أو حذف الدفعات).

### 8. فرض العزل التام وصلاحيات الأدوار الصارمة (Phase 4: Multi-Tenancy Enforcement & RBAC)
- **منظومة الصلاحيات المركزية (Centralized Permissions System)**:
  - تعريف مصفوفة صلاحيات تفصيلية عبر مصفوفة `ROLE_PERMISSIONS` ودوال إعادة استخدام مثل `requirePermission()`, `requireRole()`, `getTenantContext()`, `assertTenantOwnership()`, `assertResourceOwnership()`.
  - **فصل المهام المالية (Separation of Financial Duties)**:
    - مدير الشركة (`COMPANY_ADMIN`) يملك إدارة الوحدات وتحديث الأسعار وسجلات التدقيق لكنه **لا يملك** اعتماد العقود أو تسجيل الدفعات.
    - مسؤول المبيعات (`SALES_AGENT`) يملك إنشاء العملاء وإدارة عملائه وحجز الوحدات ومسودات العقود، ولا يملك تعديل الأسعار أو اعتماد العقود أو تسجيل الدفعات أو الاطلاع على عملاء مندوب آخر.
    - المحاسب (`ACCOUNTANT`) يملك حصرياً اعتماد العقود وتحصيل الدفعات، ولا يملك تعديل العملاء أو الوحدات أو الأسعار.
- **التحقق الدقيق من ملكية الموارد (Ownership Validation)**:
  - التحقق من ملكية الشركة لكل مورد مستهدف قبل القراءة أو التعديل عبر دمج `companyId` من الجلسة الموثقة.
  - قيد ملكية مندوب المبيعات: منع مندوب المبيعات من استعراض أو تعديل بيانات عميل أو حجز يتبع لمندوب مبيعات آخر حتى داخل نفس الشركة برمز خطأ `403 Forbidden`.
- **الحماية من الإسناد الجماعي (Mass Assignment Protection)**:
  - استخدام مخططات Zod صارمة تحدد الحقول المسموح بها صراحة.
  - تطبيق دالة `stripMassAssignmentFields` لتطهير المدخلات من أي محاولات لتمرير `role`, `companyId`, `createdById`, `status`.
  - منع المستخدمين قطعياً من ترقية صلاحياتهم أو تغيير شركتهم التابعين لها.

## الافتراضات الموثقة (Documented Assumptions)

1. **انتهاء الحجز بعد 72 ساعة**:
   - يتم تحديد `expiresAt` تلقائياً بـ `now + 72 hours`.
   - يتم تنفيذ مسح دوري وتلقائي (Lazy Cleanup & Sweeper) عند كل عملية استعلام أو حجز للوحدات لتحويل الحجوزات المنتهية إلى `EXPIRED` وإعادة الوحدة تلقائياً إلى حالة `AVAILABLE`.
2. **سقف الخصم 5%**:
   - تم تقييد الخصم في 3 طبقات دفاعية:
     1. قيد قاعدة البيانات: `CONSTRAINT "discount_max_5_percent" CHECK ("discountPercent" <= 5)`.
     2. طبقة التحقق البرمجية (Zod Schema & Service): رفض أي قيمة > 5 برمز خطأ `400 Bad Request`.
     3. واجهة المستخدم (UI): التحقق اللحظي والتنبيه الصريح للمستخدم.
3. **اعتماد العقد يغير حالة الوحدة**:
   - يتم إجراء اعتماد العقد في معاملة موحدة (`tx`) تحول العقد إلى `APPROVED` والوحدة إلى `SOLD` وتسجل في سجل الرقابة `AuditLog`.

## أبرز 3 مخاطر أمنية وكيفية معالجتها (Security Risks & Mitigations)

### الخطر 1: تسريب بيانات بين الشركات (Broken Object Level Authorization / IDOR)
- **التهديد**: قيام مستخدم بتغيير معرف الوحدة أو العقد في الطلب للوصول إلى بيانات شركة أخرى.
- **المعالجة**: عزل كامل في طبقة الخدمة `Service Layer`؛ يتم تضمين `companyId` المستخرج من الـ Session في كل استعلام قاعدة بيانات. تم كتابة اختبار آلي مخصص [`tests/security-isolation.test.ts`](file:///d:/WORK/Projects/GreenRyad/tests/security-isolation.test.ts) للتحقق من استحالة وصول شركة A لبيانات شركة B.

### الخطر 2: هجمات التسابق وتكرار العمليات (Race Conditions & Double Spending)
- **التهديد**: إرسال نقرتين متزامنتين لتسجيل دفعة أو حجز وحدة.
- **المعالجة**:
  - للحجوزات: تحديث ذري مشروط (`updateMany where status = AVAILABLE`).
  - للمدفوعات: فرض قيد فريد `UNIQUE(idempotencyKey)` في قاعدة البيانات وداخل معاملة ذرية.

### الخطر 3: التلاعب بالأسعار أو تعديل سجلات التدقيق (Data Tampering & Privilege Escalation)
- **التهديد**: تعديل سعر وحدة محجوزة أو مباعة، أو قيام موظف بحذف أفعاله من سجل الرقابة.
- **المعالجة**:
  - منع تعديل سعر أي وحدة حالتها ليست `AVAILABLE` عبر شروط برمجية وقيد تدقيق إلزامي `AuditLog` يسجل السعر القديم والجديد وهوية المعدل.
  - جعل سجل الرقابة (`AuditLog`) حقلاً للإضافة فقط (Append-Only Ledger)، ولا يُتاح الوصول إليه إلا لدور `COMPANY_ADMIN`.

### 9. المرحلة الخامسة: إدارة الوحدات والعملاء والحجوزات المتزامنة (Phase 5: Units, Clients & Reservations)
- **إدارة الوحدات والأسعار (Units & Pricing Governance)**:
  - صلاحية الإنشاء وتعديل الأسعار مقصورة حصرياً على مدير الشركة (`COMPANY_ADMIN`).
  - **قفل الأسعار الرقابي**: منع تعديل سعر أي وحدة حالتها `RESERVED` أو `SOLD` قطعياً مع إرجاع `400 Bad Request`.
  - **توثيق التدقيق الإلزامي**: تسجيل وتوثيق أي تغيير في السعر في جدول `AuditLog` متضمناً السعر القديم والجديد وهوية المعدل بالهللة والريال.
  - **حالات وانتقالات الوحدات المسموح بها**:
    - `AVAILABLE` → `RESERVED`
    - `RESERVED` → `AVAILABLE`
    - `RESERVED` → `SOLD`
    - حظر أي انتقالات غير نظامية (مثل تحويل مباشر من `AVAILABLE` إلى `SOLD` دون حجز واعتماد، أو تحويل وحدة `SOLD` إلى `AVAILABLE`).
  - **الفلترة والفرز في الخادم (Server-Side Filtering & Sorting)**:
    - فلترة حسب الحالة (`status`).
    - فلترة حسب الحد الأدنى والحد الأقصى للسعر (`minPrice` / `maxPrice`).
    - فرز حسب السعر تصاعدياً وتنازلياً (`priceAsc`, `priceDesc`) والمساحة (`areaAsc`, `areaDesc`) وتاريخ الإنشاء.
    - التحقق من كافة معلمات البحث عبر Zod.
- **إدارة العملاء وخصوصية الملكية (Client Management & Ownership)**:
  - إنشاء العملاء متاح حصرياً لمندوبي المبيعات (`SALES_AGENT`).
  - استخراج `companyId` و `salesRepId` (`createdById`) حصرياً من جلسة المستخدم الموثقة لمنع الإسناد الجماعي.
  - عزل بيانات العملاء: لا يمكن لمندوب المبيعات استعراض أو تعديل سوى العملاء المنشئين من قبله شخصياً.
  - عرض ملاحظات العميل ومتطلباته العقارية بوضوح في الواجهة التفصيلية للعميل.
- **محرك الحجوزات الذري والحماية من التسابق التزامني (Atomic Concurrency Engine)**:
  - محاولة مندوبين حجز نفس الوحدة في نفس اللحظة: يُنفذ تحديث ذري مشروط:
    ```sql
    UPDATE "units"
    SET "status" = 'RESERVED'
    WHERE "id" = :unitId AND "companyId" = :companyId AND "status" = 'AVAILABLE';
    ```
  - التحقق الصارم من عدد الصفوف المعدلة (`affectedRows.count === 1`). إذا كان 0، يتم التراجع الفوري ورمي استثناء نزاع `409 Conflict`.
  - مدة الحجز محددة بدقة بـ **72 ساعة** متطابقة مع توقيت الخادم وقاعدة البيانات (`Date.now() + 72 * 3600 * 1000`).
  - إنشاء الحجز، قفل الوحدة، وتسجيل التدقيق داخل معاملة ذرية موحدة `prisma.$transaction`.
- **نظام الانتهاء التلقائي (Automatic 72-Hour Expiration)**:
  - **المسح الكسول (Lazy In-Flight Sweeper)**: يُفحص ويُعاد تدوير أي حجز منتهي فوراً عند أي طلب استعلام عن الوحدات أو محاولة حجز جديدة.
  - **العامل المجدول (Expiration Worker & Cron)**:
    - تشغيل دوري كعملية خلفية (Daemon): `npm run worker:expiration -- --daemon`.
    - مسح فوري بطلب واحد: `npm run worker:expiration`.
    - نقطة نهاية برمجية للجدولة السحابية: `POST /api/cron/expire-reservations`.
  - **القيد الرقابي الأهم (Sold Invariant)**: لا يمكن نهائياً إعادة وحدة لحالة `AVAILABLE` إذا كانت حالتها `SOLD` حتى لو انتهت مدة الحجز الأصلية.

### المرحلة السادسة: إدارة العقود وجداول الأقساط (Phase 6: Contracts & Installments)
- **إنشاء مسودة العقد (Draft Creation)**:
  - متاح حصرياً لمندوب المبيعات (`SALES_AGENT`) ومن حجز فعال غير منتهي الصلاحية يملكه المندوب نفسه.
  - استرداد سعر الوحدة الأصلي حصرياً من قاعدة البيانات دون الوثوق بأي مدخلات من واجهة المستخدم.
  - تطبيق سقف الخصم الصارم (5% كحد أقصى) مع رفض الخصومات السالبة أو التي تتجاوز 5% في الخادم.
  - التحقق من الدفعة الأولى: لا يمكن أن تكون سالبة ولا يمكن أن تساوي أو تتجاوز السعر النهائي.
  - الحسابات المالية بالكامل عبر `Prisma.Decimal` والهللات بالـ `BigInt` (انعدام تام لاستخدام `Float` أو `Double`).
  - منع إنشاء أكثر من مسودة عقد للحجز نفسه.
- **توليد جدول الأقساط الشهرية (Installment Generation Engine)**:
  - المبلغ المتبقي بعد الدفعة الأولى مقسوم بالتساوي على عدد الأقساط.
  - توزيع باقي القسمة بالهللات بالكامل على **القسط الأول** لضمان تطابق مجموع الأقساط مع الدفعة الأولى بدقة متناهية حتى آخر هللة.
  - معادلة الاستحقاق الشهري (قاعدة تثبيت اليوم المرجعي Anchor Day):
    - الحفاظ على يوم البداية كمرجع شهري ثابت.
    - تقريب الأشهر الأقصر لآخر يوم في الشهر (31 يناير ← 28 فبراير في السنوات العادية أو 29 فبراير في السنوات الكبيسة).
    - العودة التلقائية لليوم المرجعي الأصلي في الأشهر اللاحقة (31 يناير ← 28 فبراير ← 31 مارس).
- **حالات الأقساط (Installment Status)**:
  - `PENDING`: قسط مستحق لم يُدفع منه شيء ولم يحل تاريخ استحقاقه.
  - `PARTIAL`: قسط مدفوع جزئياً.
  - `PAID`: قسط مسدد بالكامل.
  - `OVERDUE`: قسط حل تاريخ استحقاقه ولم يُسدد بالكامل (تقييم ديناميكي لحظي في الخادم والواجهة).
- **اعتماد العقود المحاسبي وحصانة العقود المعتمدة (Accountant Approval & Immutability)**:
  - متاح حصرياً للمحاسب المالي (`ACCOUNTANT`).
  - التحقق من فاعلية الحجز وعدم انقضاء مدته الـ 72 ساعة، والتحقق من بقاء الوحدة في حالة `RESERVED`.
  - تنفيذ تحديث ذري مشروط داخل معاملة موحدة `prisma.$transaction`:
    - تحويل حالة الوحدة فوراً إلى `SOLD`.
    - تحويل حالة العقد إلى `APPROVED` وتوثيق `approvedById` و `approvedAt`.
    - تحويل حالة الحجز إلى `CONVERTED`.
    - تسجيل العملية في سجل التدقيق غير القابل للتعديل `AuditLog`.
  - الحصانة المطلقة بعد الاعتماد (Immutability): يُمنع منعاً باتاً تعديل الشروط المالية أو العميل أو الوحدة أو جدول الأقساط لأي عقد معتمد.
  - الحماية من سباق الاعتماد المتزامن: استخدام التحديث المشروط الذري لضمان قبول طلب واحد فقط ورفض أي طلب منافس بنزاع `409 Conflict`.

### المرحلة السابعة: سندات القبض وتوزيع الدفعات وسجلات الرقابة (Phase 7: Payments, FIFO Allocation & Audit Logs)
- **تسجيل سندات القبض والدفعات (Payment Recording Engine)**:
  - متاح حصرياً للمحاسب المالي (`ACCOUNTANT`).
  - تسجيل الدفعات مسموح فقط على العقود المعتمدة رسمياً (`APPROVED`).
  - الرفض الصارم للمبالغ الصفرية والسالبة (`amount <= 0`).
  - رفض أي دفعة تتجاوز الرصيد المتبقي الإجمالي للعقد.
  - حسابات مالية نقدية دقيقة باستخدام `Prisma.Decimal` والهللات دون أي استخدام للفواصل العشرية العائمة (`Float` / `Double`).
  - حصانة الدفعات (`Payment Immutability`): يُمنع منعاً باتاً تعديل أو حذف أي سند قبض مسجل بعد إنشائه (حظر مسارات `PUT`, `PATCH`, `DELETE`).
- **خوارزمية التوزيع المالي المتسلسل (FIFO Payment Allocation)**:
  - خدمة مخصصة ومستقلة: `PaymentAllocationService.calculateFifoAllocations`.
  - استرداد الأقساط غير المسددة أو المسددة جزئياً وترتيبها تصاعدياً بحسب تاريخ الاستحقاق (`dueDate ASC`) مع استخدام رقم القسط (`installmentNumber ASC`) كعامل حسم مستقر (`Tie-Breaker`).
  - توزيع الدفعة على القسط الأقدم أولاً حتى سداده بالكامل، ثم الانتقال للقسط التالي حتى نفاد كامل مبلغ الدفعة.
  - دعم السداد الجزئي للقسط وتحديث حالته إلى `PARTIAL` أو `PAID`.
  - التحقق الصارم من المحدد الثابت: مجموع مبالغ التخصيص في السجلات يساوي بدقة تامة مبلغ الدفعة:
    $$\sum \text{Allocations} \equiv \text{Payment Amount}$$
  - تحديث حالة العقد تلقائياً إلى مكتمل السداد (`COMPLETED`) عند سداد القسط الأخير.
- **أمان المعاملات والتزامن (Transaction Safety & Concurrency Locking)**:
  - تنفيذ كامل العملية (إنشاء الدفعة، إنشاء التخصيصات، تحديث الأقساط، تحديث العقد، وإنشاء سجل التدقيق) داخل معاملة ذرية موحدة `prisma.$transaction`.
  - قفل تزامني حصري على مستوى صف العقد في قاعدة البيانات:
    ```sql
    SELECT id FROM "contracts" WHERE id = :contractId AND "companyId" = :companyId FOR UPDATE;
    ```
  - حماية مطلقة من التسابق: منع محاسبين من سداد نفس العقد بالتزامن بما يتجاوز الرصيد المتبقي.
  - التراجع التلقائي الكامل (`Rollback`) عند فشل أي خطوة دون ترك أي سجلات جزئية.
- **منع التكرار وضمان الاتساق (Idempotency Engine)**:
  - استقبال مفتاح منع التكرار (`Idempotency-Key`) إما عبر ترويسة الطلب أو حقول البيانات.
  - فرض قيد فريد في قاعدة البيانات لمنع تكرار السداد عند تكرار النقر أو إعادة محاولة الشبكة.
  - إعادة نتيجة السند الأصلي مباشرة (`isDuplicate: true`) عند تكرار الطلب بالمفتاح نفسه.
  - التعامل الآمن مع الطلبات المتزامنة بنفس المفتاح عبر التقاط الخطأ `P2002` واسترداد السجل الفائز بأمان.
- **سجلات الرقابة والتدقيق غير القابلة للتغيير (Immutable Audit Logs)**:
  - خدمة مركزية `AuditService` ومسار `GET /api/audit` مقيد حصرياً بمدير الشركة (`COMPANY_ADMIN`).
  - التوثيق الشامل للعمليات الحساسة في نفس معاملة العملية:
    - تسجيل الدفعات وسندات القبض (`PAYMENT_RECORDED`).
    - اعتماد العقود وترحيلها (`CONTRACT_APPROVED`).
    - تعديل أسعار الوحدات العقارية (`UNIT_PRICE_CHANGED`).
    - محاولات تسجيل الدخول الفاشلة والناجحة (`FAILED_LOGIN`, `LOGIN`).
  - تطهير البيانات الحساسة (`Data Sanitization`): إزالة وحجب كلمات المرور، ورموز الجلسات، والبيانات السرية تلقائياً قبل حفظها في تفاصيل السجل.
  - دعم استعراض السجلات مع التصفح بالصفحات (`Pagination`) والفلترة بحسب نوع الإجراء (`Action`) ونوع الكيان (`EntityType`) والتواريخ.
  - حظر مطلق لعمليات الحذف والتعديل (`PUT`, `PATCH`, `DELETE` تعيد 405 Method Not Allowed).

### المرحلة الثامنة: تكامل الواجهات الأمامية، إدارة الحجوزات والأقساط، والتحقق النهائي (Phase 8: Frontend Integration & Final Delivery)
- **شاشات النظام الـ 9 المتكاملة بنظام الاتجاه العربي (Arabic RTL Responsive Screens)**:
  1. **تسجيل الدخول (`/login`)**: مصادقة آمنة مع وصول سريع لكافة أدوار المستخدمين والشركتين.
  2. **لوحة التحكم والمؤشرات (`/`)**: نظرة شمولية على مؤشرات الأداء العقاري والمالي.
  3. **الوحدات العقارية (`/units`)**: إدارة الوحدات، فلترة الخادم بحسب السعر والمشروع والحالة، وتعديل الأسعار للمدير فقط.
  4. **إدارة العملاء (`/clients`)**: إدارة العملاء مع العزل التام بين مناديب المبيعات وعرض الملاحظات العقارية.
  5. **إدارة الحجوزات (`/reservations`)**: شاشة مخصصة لمتابعة الحجوزات المؤقتة مع عداد تنازلي لحظي للـ 72 ساعة، التنبيه للحجوزات التي قاربت على الانتهاء (< 12 ساعة)، التحويل لصياغة عقد، وإلغاء الحجز التلقائي أو اليدوي.
  6. **العقود والاتفاقيات (`/contracts`)**: صياغة مسودات العقود من الحجوزات النشطة واعتماد العقود للمحاسب المالي.
  7. **جدول الأقساط (`/installments`)**: شاشة مخصصة لاستعراض جدول المديونيات والأقساط المستحقة والمتأخرة ونسبة التحصيل مع إمكانية السداد الفوري للمحاسب.
  8. **المدفوعات وسندات القبض (`/payments`)**: تسجيل سندات القبض، التوزيع الآلي بنظام الأسبقية (`FIFO`)، منع التكرار المالي (`Idempotency`)، وعرض تفاصيل السند والتوزيع.
  9. **سجل الرقابة والتدقيق (`/audit`)**: سجل أمني موثق غير قابل للتعديل لمدير الشركة حصرياً.
- **التوافق والاستجابة والتنقل الذكي (SPA Navigation with Zero Reload)**:
  - تنقل فوري وسلس بين كافة التبويبات مع مزامنة كاملة لعناوين المتصفح (`window.history.pushState`).
  - معالجة حالات انتهاء الجلسات (`401 Unauthorized`) والتحويل التلقائي لصفحة تسجيل الدخول.
  - إخفاء وتأمين عناصر التحكم الحساسة بناءً على دور المستخدم (`Role-Aware UI`).
